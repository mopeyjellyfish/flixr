# Shape: Flixr core

## Problem and evidence

People who own films and TV episodes need a polished way to browse and play them on their own network without depending on a vendor account, hosted control plane, or continuous internet access. The intended household experience is as simple and high quality as a modern streaming service, while the server remains local, inspectable, and MIT licensed.

The first product must prove the complete path from files on disk to playback on a chosen screen. Supporting every media category before this path works would spread effort across incompatible metadata, navigation, and playback models and would delay a credible Plex replacement.

Decision-changing evidence:

- The accepted first content scope is films and episodic TV.
- The accepted network scope is LAN-first. WAN streaming and offline media sync are not release-one requirements.
- Browser playback remains most reliable when it tries direct play first, stream-copy/remux second, and fMP4 HLS through native HLS or MSE as the compatibility fallback. WebCodecs, AV1, and HEVC are capability-tested optimizations, not a universal playback base. See [W3C Media Source Extensions](https://www.w3.org/TR/media-source-2/), [W3C Media Capabilities](https://www.w3.org/TR/media-capabilities/), [MDN video codec guidance](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs), and [FFmpeg formats](https://ffmpeg.org/ffmpeg-formats.html).
- Google Cast and AirPlay depend on sender browser, device, secure-context, and codec support. Release one must provide Flixr-to-Flixr LAN screen control as the owned path and also expose bounded platform adapters when their prerequisites are met.
- Tailwind CSS v4 targets modern browsers. Release one therefore supports current evergreen Chrome, Edge, Firefox, and Safari on desktop and mobile. It does not promise compatibility with legacy smart-TV browsers. See the [Tailwind CSS v4 compatibility guidance](https://tailwindcss.com/docs/compatibility).

## Proposed solution

Ship one local Flixr server and one responsive web client. An owner configures film and TV library roots, creates household profiles, scans the roots, reviews the resulting catalog, and then leaves the server running. A household member selects a profile, enters its PIN when protected, browses a cinematic home view, and plays locally or on another supported screen.

The release-one installation consists of:

- one Go executable that serves the JSON interface and embedded web assets;
- one SQLite catalog with no external database requirement;
- owner-supplied library directories;
- externally installed `ffmpeg` and `ffprobe`, checked at startup and through an owner-triggered readiness recheck rather than bundled into the MIT distribution; the owner interface still starts when either tool is unavailable, `ffprobe` absence disables new scans, and `ffmpeg` absence disables remux/transcode while preserving direct play for already inspected media;
- an optional owner-supplied TMDB credential for film and TV metadata and artwork, with required attribution; and
- optional owner-configured trusted HTTPS for Google Cast and other secure-context features.

The product continues to browse known files when TMDB or the internet is unavailable. It caches imported metadata and artwork locally. Without provider metadata, it presents a usable title derived from the file and marks the item for owner review. Flixr never searches for, acquires, or downloads media content.

### Architecture direction

Use a small set of deep, domain-focused modules with explicit narrow APIs on concrete structs:

- **Catalog:** owns configured roots, path safety, scanning, `ffprobe` inspection, film and TV identity, metadata matching, artwork caching, and catalog queries. It exposes catalog outcomes, not filesystem or provider details.
- **Household:** owns the server owner, profiles, optional profile PINs, sessions, viewing progress, and administrative authority.
- **Playback:** owns client capability input, deterministic plan selection, FFmpeg remux/transcode processes, bounded temporary segment storage, leased jobs and generations, cancellation, and playback errors. Callers provide recorded media properties and ask for a plan; they do not provide file access or construct FFmpeg commands. A job groups one source/rendition key and can own multiple seek generations. Each generation owns one FFmpeg process and a server-derived context. Each attached playback session leases one generation; manifest, segment, range, or explicit heartbeat activity renews that short lease. Explicit stop or lease expiry detaches it. A generation stops when its last lease ends, and an empty job is retired.
- **Screens:** owns active Flixr screen presence, short-lived control sessions, handoff, remote play commands, Google Cast sender integration, and AirPlay route availability.
- **Web:** owns the versioned HTTP/JSON interface, authenticated byte-range delivery from size-known media handles through `http.ServeContent`, embedded client, authentication middleware, central mapping from domain errors to one JSON error shape, and an origin-checked WebSocket connection for Flixr screen control. It explicitly tracks and closes WebSockets during shutdown because `http.Server.Shutdown` does not own hijacked connections.

Start with concrete Go types and composition in `main`. "Module API" does not imply a Go interface type. Introduce consumer-defined Go interface types only where a real alternative exists, initially metadata lookup and process execution in tests. Do not create layer packages, a generic repository abstraction, a generic `Media[T]` hierarchy, or speculative plug-in seams. Films and episodic TV have distinct domain types even where catalog views can project shared display fields. Playback receives recorded media properties and client capabilities as plain values rather than importing Catalog. Expected branch points use errors owned by their domain and wrapped with `%w`; Web maps them once to stable HTTP status and error codes.

Target Go 1.25. Use current `net/http` routing, explicit server timeouts, `context.Context` for I/O and long-running work, bounded scan and transcode concurrency, structured logging, and graceful shutdown. Use `os.Root` for syscall-level containment within configured libraries. Web opens indexed relative paths through Catalog and performs byte-range delivery from the resulting size-known handle. FFmpeg receives only a generated, short-lived loopback HTTP input URL; its range-capable handler opens that same catalog ID through `os.Root`, and FFmpeg never receives a library path. Persist transactional catalog state in SQLite WAL mode through the pure-Go `modernc.org/sqlite` driver so the application remains one cross-compilable executable; serialize writes through one writer connection, set a busy timeout, and use a bounded reader pool. External clients address media only by catalog ID; they never submit a stream path.

The release-one web client uses React 19, TypeScript, Vite, and Tailwind CSS v4. Accessible headless primitives may supply difficult behavior, but Flixr does not adopt a generic visual component kit. The media player, screen coordinator, and focus manager remain deep client modules so page components send intents rather than operating HLS, Cast, AirPlay, or spatial-navigation SDKs directly. Poster rails are virtualized and player/casting code is loaded only when needed. Keep API contracts, domain state machines, playback/session policy, and design tokens free from DOM and device-SDK dependencies where release-one behavior justifies those seams; do not create speculative native packages or duplicate UI abstractions. This keeps a later Expo/React Native mobile and TV client or Tauri desktop package practical without replacing the web client with React Native Web or promising identical UI code across platforms.

The playback planner uses this order:

1. **Direct play:** serve an indexed original through authenticated HTTP byte ranges when exact container, codec, profile, audio, and subtitle capabilities are suitable.
2. **Direct stream/remux:** use FFmpeg stream copy into fragmented MP4 HLS when tracks are compatible but the container is not.
3. **Compatibility transcode:** create one on-demand H.264/AAC fragmented-MP4 HLS rendition for incompatible browser playback.

Release one records all tracks but exposes one selected audio track and no user-selectable subtitle workflow. Transcode work is keyed by the complete source and rendition, while concurrency and segment limits apply to each running seek generation and therefore to each FFmpeg process. Leases attach to generations; the enclosing job retires after its final generation. Each generation owns one directory and one bounded sliding segment window around its leased session positions. Sessions share segments only by attaching to the same live generation; no segment outlives its generation or counts more than once against global storage. A seek outside retained segments moves that session to a new generation at the requested offset; another viewer can keep the old generation alive through its own lease. Active clients continue a low-frequency heartbeat while paused; the heartbeat interval is less than half the lease TTL, and the TTL exceeds the documented transient-network-stall budget. When the page is suspended or disappears, lease expiry releases the generation and resume starts from the saved offset. The configured segment location has per-generation and global hard bounds; completed and orphaned generation directories have deterministic reclamation. FFmpeg receives discrete host-generated `exec.Command` arguments and a short-lived loopback URL, never shell text, a client path, or a client-controlled protocol. Process cancellation sends a graceful termination before forced kill and uses a bounded wait. WebCodecs can support future previews or experiments but is not required for normal playback.

Bootstrap configuration uses environment variables only for the data directory, listen address, and optional TLS certificate/key. Library roots, metadata credentials, segment directory, generation/global byte limits, and concurrency limits are persisted owner settings managed through the owner web interface, with safe defaults under the data directory. The process takes an exclusive lock on the data directory and, when different, a separate exclusive lock on the configured segment directory before opening SQLite or reclaiming segment state. Two Flixr instances cannot share a catalog or temporary storage.

Tests use small committed synthetic media fixtures generated from redistributable color, tone, and subtitle sources, with their generation command and license recorded. Each fixture is at most 10 seconds and 1 MiB, and the committed media fixture set is at most 5 MiB. Unit tests use captured `ffprobe` JSON and fake process execution. FFmpeg integration tests may skip locally when the tools are absent, but the required CI gate installs them, requires those tests to run, and fails if they are skipped.

### Vertical slices

1. **Indexed local catalog:** configure one film root and one TV root, scan representative files, inspect their media properties, persist distinct film/series/season/episode records, optionally enrich them through TMDB, and return browseable JSON.
2. **Household browsing:** create an owner and PIN-protected profiles, select a profile, browse/search film and TV rails, open details, and see loading, empty, partial-metadata, and failure states.
3. **Modern local playback:** request a capability-driven plan, direct-play a compatible file, remux a container-only mismatch, transcode one incompatible file to the H.264/AAC HLS fallback, seek within a retained window, restart cleanly for a seek outside it, resume, and stop without leaked work.
4. **Your screens:** advertise an active Flixr web client as a LAN screen, select it from another client, start/pause/seek/handoff playback, expose Google Cast in supported Chromium secure contexts through a fixed receiver compatibility profile, and expose AirPlay in supported Safari contexts.

Planning will group these dependent slices into the fewest coherent review and publication boundaries. Pitch and planning documents do not need an independent pull request; they publish with the first stable implementation delivery unit.

### Accepted interface direction

- **Person and task:** a household member on a couch selects a profile, finds a film or episode, and starts or hands off playback with a remote, keyboard, or touch device.
- **Surface mode:** couch-first responsive web application. The same information hierarchy condenses from a ten-foot TV layout to laptop, tablet, and phone rather than creating an administration-first dashboard.
- **Design authority:** greenfield product; the accepted image-backed direction is **Cobalt Signal** from the verified local design board. Review-only TheTVDB artwork demonstrated real catalog variation and is not product or publication content.
- **Desired feel:** premium modern cinema, calm and fast, with streaming-service familiarity but no copied Netflix branding.
- **Signature:** local screen readiness appears as a quiet, persistent part of playback rather than as an infrastructure dashboard.
- **Palette:** near-black `#05070C`, raised surface `#101623`, interaction cobalt `#5B8CFF`, primary text `#F6F8FF`, muted text `#AAB4C8`, and success `#64DFA0`. Cobalt communicates interaction, progress, and identity; varied media artwork supplies the rest of the color.
- **Typography:** self-host Manrope for display headings and Atkinson Hyperlegible Next for body text, metadata, and controls. Both use open font licenses. Maintain large x-height, strong weight contrast, and distance-readable focus labels.
- **Representative states:** first-run setup, profile choice and PIN entry, scan empty/progress/partial/failure, populated home, search with no results, film details, episode details, direct/remux/transcode startup, playing/buffering/error, screen available/disconnected, and Cast/AirPlay unavailable because prerequisites are unmet.
- **Responsive and accessibility constraints:** full keyboard and directional navigation, deterministic focus restoration, visible white focus ring, semantic controls, WCAG 2.2 AA contrast, reduced motion, captions for meaningful artwork, no hover-only behavior, and at least 44 CSS-pixel touch targets where layout permits. TV, desktop, tablet, and phone receive explicit visual validation.
- **Operation needs:** the owner can see scan state, last successful scan, unmatched items, FFmpeg availability, active transcodes, screen availability, and actionable errors without exposing those controls in the viewing-first home hierarchy.
- **`DESIGN.md` disposition:** create a durable `DESIGN.md` from this accepted direction during planning. Do not include review-only third-party artwork; preserve tokens, hierarchy, focus behavior, responsive rules, and evidence sources.

## Boundaries and no-gos

- Films and episodic TV only. Music, comics, books, audiobooks, photos, home videos, live TV, and DVR require later pitches based on their own behavior.
- LAN-first only. No hosted Flixr account, relay, server discovery service, telemetry, federation, WAN access automation, or remote streaming guarantee.
- No offline media download or sync and no service worker in release one. Losing internet access must not affect the local server-backed catalog; losing the local server is not an offline-client mode.
- No media acquisition, torrent, usenet, ripping, store, or content-deletion workflow.
- No full adaptive bitrate ladder, HDR-to-SDR tone mapping, hardware-specific encoder matrix, pre-transcode farm, or user-authored playback profiles. These are later playback slices.
- No selectable audio-track or subtitle interface in release one. Files remain indexed with their tracks so this can be added without rescanning.
- No native mobile, TV, or desktop applications. Current browsers and supported Cast/AirPlay devices are the release-one clients.
- No guarantee for proprietary smart-TV browsers or codecs that the planner cannot direct-play or convert to the one fallback.
- No arbitrary filesystem browsing through the HTTP interface. The owner configures roots; clients use catalog IDs.
- No runtime plugin loader, Hookr integration, package manager, marketplace, or third-party UI contribution in release one. Preserve small module interfaces, then shape a separate plugin platform from evidence after the film/TV path is stable.
- No generic all-media schema, plug-in marketplace, microservices, message broker, external database, GraphQL, or speculative abstraction layer.
- Do not bundle an FFmpeg binary until its exact build configuration and LGPL/GPL distribution obligations have an accepted licensing plan.

Acceptable cuts are visual flourish, recommendations, automatic collections, trailers, cast biographies, theme songs, intro detection, chapter previews, and background file watching. Manual rescan, deterministic browse, and reliable playback cannot be cut.

Reshape if platform casting requires a hosted Flixr control plane, if trusted local HTTPS cannot provide an acceptable Cast setup, if TMDB terms conflict with the intended distribution, if representative household files cannot be handled by direct/remux/one-fallback playback, or if another media category becomes a prerequisite before the film/TV path is complete.

## Decision-changing research and risks

- **Codec and browser diversity:** extension-based guessing is not sufficient. `ffprobe` inspection and exact client capability input are required before playback planning.
- **Transcoding cost:** software H.264 fallback can saturate low-power servers. Release one limits concurrency and reports capacity errors. Hardware acceleration remains a measured later slice, not an assumed abstraction.
- **Platform casting:** Google Cast and AirPlay are not symmetric. The product must show availability from runtime capability and deployment state, not render dead controls. Flixr screen control is the guaranteed owned LAN behavior.
- **Trusted HTTPS:** secure-context casting can make first-time local setup harder. Release one documents owner-managed certificate and DNS configuration and keeps basic local browse/play plus Flixr screens usable without a hosted service.
- **Metadata identity:** filename matching can be wrong. Provider failure cannot hide files, and owner-visible unmatched state is required. Manual metadata editing beyond selecting among candidate matches can be deferred.
- **Artwork and provider rights:** review mock-ups used publicly reachable TheTVDB artwork only as temporary private evidence. Product artwork comes from the configured provider under its terms and attribution requirements; test fixtures must be original or redistributable.
- **MIT distribution versus media dependencies:** the Flixr source can be MIT while FFmpeg builds and codec libraries carry separate obligations. Keeping FFmpeg external in release one prevents the application artifact from silently changing license obligations.
- **Tailwind browser floor:** Tailwind CSS v4 is an accepted modern-browser choice. Legacy TV browser support must not force hidden compatibility hacks; such clients use Cast/AirPlay or a current Flixr screen instead.
- **Temporary media storage:** on-demand segments can exhaust a server disk or survive an unclean exit. Release one requires a configured segment directory, a hard byte bound, cleanup when the final session detaches, and startup reclamation of orphaned generation directories.
- **Synthetic fixture gate:** media integration proof depends on external FFmpeg tools. The normal unit suite remains useful without them, while the required CI acceptance gate makes their presence and execution explicit.
- **Plugin timing:** Pi-level extensibility includes scoped discovery, trust, installation, pinning, updates, lifecycle, state, UI contribution, provenance, and failure behavior; it is a product surface, not only a hook runner. Hookr is a promising typed WASM candidate for a later bounded metadata-provider pilot, but defining that public contract before Flixr has two real implementations would freeze guesses and delay the core outcome. See [Pi extensions](https://pi.dev/docs/latest/extensions), [Pi packages](https://pi.dev/docs/latest/packages), and [Hookr](https://github.com/mopeyjellyfish/hookr).

## Observable acceptance criteria

- **AC-001 — Local first run and claim:** On a clean data directory, Flixr takes an exclusive data-directory lock, generates a one-time owner setup token, and prints it to the local console/log. A browser must present that token to create the first owner, after which it is invalidated. Missing tools appear as actionable readiness states. `ffprobe` absence disables new scans; `ffmpeg` absence disables remux/transcode but permits direct play of already inspected compatible media. After installing either tool, the owner can recheck readiness without restarting Flixr, configure one film root and one TV root, and continue when required capabilities are ready.
- **AC-002 — Deterministic film and TV scan:** A manual scan of documented committed synthetic fixtures creates films and series with seasons and episodes, records container and track properties, reports unmatched and failed files, and produces the same catalog when rerun without file changes. The fixture source, generation command, and redistributable license are recorded.
- **AC-003 — Offline catalog:** After one successful enriched scan, disconnecting internet access does not prevent profile selection, catalog browse, cached artwork display, search, detail views, or playback of local files. A never-enriched file remains visible through derived local metadata.
- **AC-004 — Safe rescan:** Adding, changing, moving, and removing fixture files updates only affected catalog records and viewing relationships, never exposes a path outside configured roots, and reports partial failure without discarding the last valid catalog.
- **AC-005 — Household profiles:** The owner can create, rename, protect, and unprotect profiles. A protected profile requires its PIN, failed attempts are rate-limited, and one profile cannot read or overwrite another profile's progress through the HTTP interface.
- **AC-006 — Responsive cinematic browse:** The accepted Cobalt Signal home, search, film detail, episode detail, and profile flows work at named TV, desktop, tablet, and phone viewports with real representative content, virtualized rails, no clipped focal action, and no hover-only operation.
- **AC-007 — Accessible couch control:** A keyboard or directional remote can enter and leave navigation, move across and between rails, open and close details, operate the player, and restore focus to the originating item. Focus is always visible, reduced motion is respected, and automated accessibility checks have no serious or critical findings in the focal flows.
- **AC-008 — Capability-driven plan:** Given recorded media properties and a declared client capability fixture, the playback module deterministically returns direct play, remux, fallback transcode, or an actionable unsupported result without constructing work in the HTTP handler or React view.
- **AC-009 — Direct play:** A compatible representative file starts through authenticated HTTP range delivery, seeks without restarting from byte zero, records progress to the active profile, and resumes from that position on another client.
- **AC-010 — Remux, fallback transcode, and seek:** A container-only mismatch plays through stream-copy fragmented-MP4 HLS, and one incompatible representative file plays through the H.264/AAC fragmented-MP4 HLS fallback. Seek within the retained window reuses available segments. Seek outside it starts a new generation at the target offset and retires the old generation only after its final lease ends. A single-session generation releases resources after explicit stop or lease expiry; a shared generation remains alive while any attached lease is valid, and its enclosing job retires after its final generation.
- **AC-011 — Bounded playback work and liveness:** The configured concurrency limit counts every running seek generation and therefore every FFmpeg process, including multiple generations under one source/rendition job. Per-generation and global segment bounds apply independently of job count. Identical complete rendition keys share data only by attaching to the same live generation; one viewer's detach does not interrupt another, and no segment survives its generation. Manifest, segment, range, or heartbeat activity renews only that session's short generation lease, including a low-frequency heartbeat while a visible client is paused. The heartbeat interval is less than half the lease TTL, and the TTL exceeds the documented transient-network-stall budget. A closed, crashed, suspended, or disconnected client stops renewing; expiry decrements the generation reference count and eventually terminates abandoned work. Excess work returns an actionable capacity state. No client can inject an FFmpeg argument, protocol, or path.
- **AC-012 — Flixr screens:** Two supported web clients on the same LAN can identify one as an available screen, establish a short-lived authorized session, start/pause/seek playback from the other, hand playback back, and recover visibly when either client disconnects.
- **AC-013 — Google Cast:** Under documented trusted-HTTPS prerequisites, a supported Chromium client detects an available Google Cast target and requests a plan using Flixr's fixed Cast receiver compatibility profile rather than the sender browser's capabilities. The planner direct-plays or remuxes media that fits that profile and otherwise uses the H.264/AAC fallback. Cast starts through a short-lived signed URL. The sender consumes receiver status events and reports playback position to the active profile. It reports unavailable, rejected, disconnected, and playback-error states without exposing a permanent media URL.
- **AC-014 — AirPlay:** On a supported Safari client with an available route, the player exposes the native AirPlay picker and supplies the receiver with the same short-lived planner-approved signed media URL class used for Cast. The sender consumes available route/playback state and remains responsible for reporting progress to the active profile. It reports route loss, URL expiry, or unsupported media through the same playback state model. Other browsers do not render a dead AirPlay control.
- **AC-015 — Owner operations and configuration:** The owner view shows last scan outcome, current scan progress, unmatched items, tool readiness with a recheck action, active playback generations, and connected screens. It persists library roots, metadata credentials, segment directory and byte limits, and generation concurrency limits. Viewing profiles cannot access owner operations. Bootstrap data directory, listen address, and optional TLS paths come from documented environment variables and require restart when changed.
- **AC-016 — Local security:** The one-time first-owner setup token is required and invalidated after claim. Owner credentials and profile PINs are salted and memory-hard hashed, authenticated browser sessions use HttpOnly same-site cookies, state-changing requests enforce same-origin protection, WebSocket upgrades validate `Origin` and short-lived screen authority, Cast and AirPlay URLs expire, the internal FFmpeg input URL is loopback-only, generation-scoped, and range-capable, and catalog/stream interfaces reject traversal, symlink escape, protocol injection, and unknown IDs.
- **AC-017 — Graceful lifecycle:** Cancellation propagates through scans, provider calls, playback sessions, and HTTP requests. Server shutdown stops accepting work, closes tracked WebSockets, drains bounded in-flight work, gracefully terminates then forcibly bounds owned FFmpeg processes, closes the database, and does not corrupt the last valid catalog.
- **AC-018 — Performance budgets:** On a documented reference machine with 10,000 indexed items, paginated local browse/search requests meet a recorded p95 target of 200 ms excluding artwork transfer, the home view does not create DOM nodes for the complete catalog, and player/casting bundles are absent from the initial profile-selection route.
- **AC-019 — Bounded segment storage:** The owner configures a temporary segment directory plus per-generation and global hard byte limits. Each generation owns one directory and only a bounded sliding window around active leased positions. Sessions reuse segments only by sharing a live generation; segments never survive generation retirement and count once against global storage. A seek outside the retained window starts a new generation at the requested offset, and every generation counts against process and storage limits. Completed, cancelled, and lease-expired generations reclaim their directory. Flixr exclusively locks both the data directory and any distinct segment directory before startup reclamation, removes orphaned generation directories from an unclean prior exit, and returns an actionable capacity state instead of exceeding a limit.
- **AC-020 — Required media integration gate:** The default unit suite passes with process fakes when FFmpeg is absent. The named CI acceptance job installs `ffmpeg` and `ffprobe`, fails when any required media integration test is skipped, and proves direct play, remux, fallback transcode, in-window and out-of-window seek, paused heartbeat/TTL invariants, explicit cancellation, abandoned lease expiry, per-generation limits and directory lifetime, shared-generation lifetime, loopback range input, exclusive data and segment locking, and orphan cleanup against the bounded committed synthetic fixtures.
